# Decisions

Deviations from PLAN.md and facts verified against the real machine.

## Stage 0

- **Module path.** `github.com/EdrenaVosh/squadup`. The owner login was read from the author's GitHub account (read-only profile lookup) and matches the project link the author gave.
- **Toolchain.** Installed with Homebrew on 2026-10-24: Go 1.27.3, golangci-lint 2.15.0, GoReleaser 2.x. `go.mod` pins `go 1.27.3`.
- **Claude Code 2.1.309 flags checked with `claude --help`.** `--agents <json>`, `--agent <agent>`, `--settings <file-or-json>` and `--setting-sources <sources>` exist. `--setting-sources` is the candidate for the `--isolated` flag of `squad run` (stage 3); it is not yet verified to hide global agents.
- **Login is per config directory.** `CLAUDE_CONFIG_DIR=<empty dir> claude auth status` prints `loggedIn: false`, `authMethod: none` and exits with code 1. Consequences: `make try-claude` asks for a fresh login inside the sandbox, and `squad doctor` run under the sandbox reports "not logged in". The JSON is still printed on exit code 1, so the parser reads stdout regardless of the exit code.
- **Test stub.** `claude` is replaced in tests by `testdata/fakeclaude`, compiled once per test run and put first on `PATH`.
- **CI is unverified.** `.github/workflows/ci.yml` cannot run until the repository is pushed (stage 8). Action versions (`checkout@v4`, `setup-go@v5`, `golangci-lint-action@v8`) should be re-checked then.
- **`squadup` alias and Homebrew tap** are release concerns and land in stage 7; the GoReleaser config currently builds `squad` only.

## Stage 1

- **`claude auth status` migrates the config; `claude -v` does not.** Verified on Claude Code 2.1.309 against a sandbox: `auth status` is a full Claude Code startup. It rewrote `settings.json` (reformatted it, turned `"model": "opus"` into `"opus[1m]"`, moved `theme` to the end) and created `.claude.json`, `backups/`, `projects/`, `sessions/`. Consequences: (1) squad captures Initial *before* any command runs, so the snapshot is never taken after such a migration by squad itself; (2) `doctor` and `status` call `auth status`, which has the same effect as the user starting `claude` once; (3) in stage 2 drift detection for `settings.json` must compare the parsed values of the managed keys, not bytes, because Claude Code reformats the file on its own; (4) `squad restore` writes the snapshot values back, so it also undoes such a migration of a managed key.
- **First-run summary goes to stderr**, so `--json` output on stdout stays machine-readable. The plan only says "before the command output".
- **Initial layout.** Besides `preset.yaml` and `agents/**/*.md` the snapshot holds `initial.json` (what was captured: existence of the agents dir and settings.json, per-file sha256 and validity, raw JSON text of each managed key) and `settings.orig.json` (the original settings.json byte for byte, only if it existed). Restore needs both. Files are 0400. `settings.orig.json` may contain the user's `env` values; nothing is ever printed from it and the directory stays under `~/.squadup`.
- **Managed values are kept as raw JSON text** inside `initial.json` (a string per key). `encoding/json` would compact a `RawMessage`, losing the original formatting that byte-exact restore needs.
- **goccy/go-yaml v1.19.2 panics** when a struct has an `inline` map field and decoding is `Strict()`. Unknown keys of the `permissions` object are therefore stored under an explicit `extra:` key in `preset.yaml`. The library's last release is from January 2026; `tidwall/sjson` has had no release since 2022 (stable, but noted for stage 2).
- **Frontmatter key order** follows the field list in the plan's table of Claude Code fields (`... permissionMode, maxTurns, ..., effort, ..., color`). The example agent in the plan puts `effort` before `permissionMode`; the table wins. An untouched agent file is always written back unchanged, so the order only matters for files squad rewrites.
- **Agent scanning** follows symlinked `.md` files and skips symlinked directories and dangling links. Files are sorted by path; when two files carry the same agent name the first one by path wins in `capture` and the other is reported as skipped.
- **Exit code 2** is used for an invalid or reserved preset name (validation failure); unknown commands and flag errors stay at 1.
- **Terminal detection** is a character-device check that excludes the null device. It replaces a terminal library until the Charm stack arrives in stage 4.
- **Recapture** is refused while a preset is equipped: the live config then contains the preset, not the original setup.
- **Not verifiable on this machine:** Windows behaviour (paths, read-only files, rename over existing files) is covered only by the CI matrix once the repository is published.

## Stage 2

- **`sjson` cannot add a key tidily.** On a pretty-printed file `sjson.SetRaw` appends `\n,"model":"sonnet"}` and drops the final newline, so add-then-delete is not byte-exact. Replacing and deleting keys are fine and are still done with `sjson`; adding a key is `settings.Apply`'s own code, which appends in the document's style (indent, tabs, CRLF, compact) and is covered by round-trip tests. The plan's claim that `sjson` keeps formatting holds only for replace and delete.
- **Exact restore.** `state.json` stores the sha256 of `settings.json` right after squad wrote it. If the file still has that hash, `restore` and `undo` put the original bytes back (or delete the file when it did not exist), which makes `use A → use B → restore` byte-exact by construction. If the file changed since (Claude Code reformats it on start, the user edits it), the managed keys are edited surgically with `sjson`/`settings.Apply`, and every other key keeps whatever it has now.
- **Restore on an untouched setup is a no-op.** When nothing is equipped, `squad restore` says "Already on Initial" and writes nothing. Otherwise it would undo what Claude Code itself did to `settings.json` (see the stage 1 note on `auth status`).
- **What counts as manual edits (drift).** Agent files squad wrote are compared by hash. In `settings.json` only the managed keys the preset sets itself are tracked, and by parsed value, so reformatting is not drift. Keys that fall back to Initial are not tracked; switching presets resets them to their Initial values, as the plan says.
- **Deciding about manual edits.** On a terminal `use`/`undo` ask `[s]ave / [d]iscard / [c]ancel`; without one they stop and require `--save-edits` or `--discard-edits`. `--yes` confirms the plan but never answers this question. "Save" writes the edited agent files (a deleted file drops the agent) and changed managed keys into the equipped preset and rewrites its `preset.yaml`, which loses comments in a hand-edited file; that save is not rolled back if a later step fails.
- **Conflicts stop and are explained instead of asked.** A file at a target path that squad did not write, or another agent with the same name, is listed under "Cannot continue" and the command exits 1; `--force` overwrites files at target paths (a backup is taken first). Duplicate names are never forced. A modified Initial agent survives replace mode with a warning, and `restore` then needs `--force` to put the snapshot version back.
- **Ownership rule.** squad may overwrite or delete a file only if it is in the manifest of the equipped preset, or if it is byte-identical to the Initial snapshot. Everything else is left alone.
- **Backups** are the state *before* an operation: the whole agents folder, `settings.json`, `state.json`, plus `backup.json`. The newest 20 are kept; the old-Initial folders made by `initial --recapture` are not counted. Ids are timestamps to the second with `-2`, `-3` suffixes for operations in the same second.
- **Undo.** `squad undo` returns to the state before the last journaled operation; `--to <id>` returns to the state before any operation in `squad log`. Undo takes its own backup first, so undoing an undo is a redo. Files squad did not write are never removed by undo.
- **Failure handling.** All writes happen under `~/.squadup/.lock` (a file created exclusively; a crashed process leaves it behind and the error says to delete it). If a write fails halfway, completed steps are reverted from in-memory copies, and the backup folder remains as a second safety net. The journal line is written last.
- **File modes.** Agent files are written 0644; `settings.json` keeps its current mode, or 0600 when squad creates it; everything under `~/.squadup` is 0600.
- **Model availability** is not checked by `use` yet: the model catalogue and the probe belong to stage 3.
- **Dry run with conflicts** exits with 1, so a script can tell that the real run would not go through.
- **`testscript.RunMain` is deprecated** upstream; the e2e runner uses `testscript.Main`. Scripts remove every `PATH` entry holding a `claude` binary, so they never start the developer's real Claude Code.

## Stage 3

Checked against Claude Code 2.1.309, its `--help`, and the documentation of 2026-10-24.

- **No `--isolated` flag for `squad run`.** Claude Code has no way to hide `~/.claude/agents` and still keep `--agents`: `--setting-sources` selects settings files only, `--safe-mode` turns off every custom agent (the `--agents` ones too), and `--bare` skips subagent discovery but also never reads OAuth or the keychain, so it needs `ANTHROPIC_API_KEY`. `squad run solo -- --bare` still works for someone who wants it, because everything after `--` goes to claude. The run notice says "(+ your global agents)".
- **`--agents` content was checked with the real validator.** Claude Code validates the value at startup ("Invalid --agents configuration"). A preset with an agent that uses 16 different fields (tools, hooks, maxTurns, memory, isolation, …) passes; `color` and `experimental` are dropped because `--agents` ignores them. `tools` written as `Read, Grep` becomes an array, as in the documentation's example. The `/agents` wizard no longer exists in Claude Code, so whether the agents are visible inside a live session can only be seen by asking Claude, which costs a request: left for the manual check.
- **Size limit.** A single `--agents` argument may not exceed 120 KB (30 KB on Windows, whose whole command line is limited to about 32 KB). A larger preset is refused with advice to use `squad use`. The file form of `--agents` exists only together with `-p`.
- **Settings for `run`.** The temporary `--settings` file carries `model`, `effortLevel` and `permissions`: what the preset sets, and Initial's value for the keys it leaves out, so a preset equipped at the moment does not leak in. `--settings` cannot delete a key, so a key that the live `settings.json` has and Initial does not stays as it is. The main agent goes through `--agent`.
- **`effortLevel` does not accept `max`** in settings (only low, medium, high, xhigh), although an agent's own `effort` does. `preset.Validate` now rejects it, which also stops `squad use` early. This corrects the plan's single list of effort levels.
- **The model probe reads `modelUsage`.** The JSON result of `claude -p --output-format json` has `modelUsage`, keyed by the model name; Claude Code also lists helper models there, so the key that mentions the requested alias wins. This is taken from the Agent SDK reference (`SDKResultMessage`), **not yet from a live answer**: `squad models --probe` was exercised only against the test double. The first real `--probe` is the check. A probe runs `claude -p "Reply with OK" --model <alias> --output-format json --no-session-persistence` in the temp directory, so it saves no session and loads no project hooks.
- **Consent for the probe** is the `--probe` flag itself; plain `squad models` never spends tokens. The first-run offer to probe belongs to the TUI.
- **Policy.** `availableModels` is read from the user's `settings.json` and from file-based managed settings (`/Library/Application Support/ClaudeCode`, `/etc/claude-code`, `C:\Program Files\ClaudeCode`, plus `managed-settings.d/*.json`). `deniedModels`, `enforceAvailableModels` and `availableModelsMatch` count only from managed settings, as documented; `deniedModels` in user settings is reported as ignored. Policy that arrives through an MDM profile or the claude.ai console cannot be read, and project and local settings are not read either. How drop-in files combine is not documented in detail: later files override earlier ones per key.
- **Statuses.** `verified` (a probe succeeded, or the name always works: `inherit`, `default`), `allowed by policy` (the allowlist names it, no probe), `unknown`, `unavailable` (policy forbids it or the probe failed, with the reason). The policy can only take a model away. `[1m]` names stay `unknown` after a successful probe because the 1M window is not probed.
- **Cache.** `cache/models.json` is valid for 24 hours and for the same `claude -v` and `authMethod`. `use`, `run` and `status` read it with the version check only where the account type is not at hand, so they never start an extra `claude auth status`.
- **Unavailable models in `use`/`run`** are warnings with the advice to edit the agent or set `model: inherit`. The plan's "offer to replace with inherit" is an interactive step that waits for the TUI.
- **`squad lint` without a name** checks every stored preset and Initial. Exit code 2 means errors; warnings pass unless `--strict`. Severity: error for what breaks squad or Claude Code (unreadable file, bad or duplicate name, missing description, bad field values, preset validation, missing agent file, name that differs from the file in a preset); warn for likely mistakes (unknown field with a "did you mean" within edit distance 2, description shorter than 40 characters or without use/when/after/before, descriptions with ≥ 0.8 word overlap, empty prompt, a main agent outside the preset, `bypassPermissions`, `Bash`/`Bash(*)`/`WebFetch` in `allow`, unknown color); info for notes (no `tools` list, `auto`/`dontAsk`, a preset without agents). `manual` is accepted as an alias of `default` in `permissionMode`, and `experimental` is a known field.
- **Cost estimate** is characters ÷ 4 rounded up, counting the name and description of every agent as the per-session cost and the prompt as the cost per call.

## Stage 4

- **Charm v2 line** (`charm.land/bubbletea/v2`, `lipgloss/v2`, `bubbles/v2`, `teatest/v2`) is used: it is the current stable one. **`huh` is not used**: the agent editor needs a dense 80×24 field list with a live preview and lint hints, which a form library would not lay out; `bubbles` text inputs and own choice lists do it. A cursor that does not blink keeps screens and tests deterministic.
- **The interface opens only on a real terminal** (stdin and stdout), without `NO_COLOR`, `CI`, `--no-color` or `TERM=dumb`; otherwise bare `squad` prints help and the first-run summary stays text.
- **Shared layer.** `internal/workspace` holds list, create, clone, rename, remove, capture, lint, card data, model warnings and the model probe; the CLI and the interface both use it.
- **Every edit is saved at once** (no explicit save). Choosing "Custom…" permissions changes nothing until a rule is edited.
- **Templates** (plan stage 5) are not offered on the welcome screen yet. The unavailable-model offer to switch to `inherit` stays a warning.
- **Tests.** Screens are checked as golden 80×24 text (`go test ./internal/tui -screens` rewrites them), flows by driving the model, and one scenario runs the real program through `teatest`. The interface code was written before its tests; mutation checks on its key logic were run afterwards.
- **Not verified by a human:** how the screens look and feel in a real terminal; the Try action (`t`, which hands the terminal to claude) is not covered by tests.

## Stage 5

- **Exchange format.** One preset is `{"format":"squadup-preset","schema":1,"generator","exportedAt","preset":{…},"agents":[{"file":"x.md","content":"…"}]}`; `--all` writes `{"format":"squadup-presets",…,"presets":[{preset, agents}…]}`. The agent list of the preset is the order of the `agents` array, and agent files travel as text, so a file that is not UTF-8 is refused on export. Only `model`, `effortLevel` and `permissions` of the settings are exported: `env` and everything else never leave the machine.
- **Import never applies and never writes outside the library.** Checks, in order: JSON and size (≤ 1 MB), format and schema (a newer schema is refused), file names (`<name>.md` in lowercase letters, digits and dashes — no paths, `..`, subfolders), the name inside each file must match its file name, the preset must validate, and `main` must be one of its agents. Unknown frontmatter fields are kept; `squad lint` shows them.
- **Consent.** `permissionMode` or `defaultMode` of `bypassPermissions`, `dontAsk` or `auto` is a *danger*: the import needs `--accept-risks`, or a yes at the prompt on a terminal. `--yes` deliberately does not count, and neither does piping the file through stdin, which cannot ask. `Bash`, `Bash(*)` and `WebFetch` in `allow` are warnings. `hooks` and `mcpServers` of agents are removed unless `--allow-hooks` (or `h` in the interface); the commands they would run are listed either way. Anything that looks like a key (`sk-…`, `ghp_…`, `AKIA…`) in an imported file is a warning.
- **Export scan.** The same three patterns are looked for in every agent file before anything is written; the report masks the keys. A hit stops a non-interactive export unless `--yes`.
- **Name collisions.** A taken or reserved name gets `-2`, `-3`, …; `--as` picks the name (and fails if it is taken); `--force` replaces the preset that has the name. `--as` with a collection is refused.
- **Sources.** A path, `-` (stdin), an `https://` link (redirects to http are refused; 30 s; ≤ 1 MB) or `gist:<id>`. Gists go through the `gh` CLI (`gh gist view <id> --files`, then `--filename … --raw`; `gh gist create --filename <name>.squad.json -`, which makes a *secret* gist); the file ending in `.squad.json` is taken, or the only file. Without `gh` the error says how to install it. `gh` flags were checked against the manual at cli.github.com; **the real `gh` was never run** — tests put a stub first on PATH (`testutil.FakeGH`), so the first real `--gist` is a manual check.
- **Templates** live in `templates/<id>/` (the same layout as a stored preset) and are embedded. Each lints with no warnings (a test enforces it, together with "every prompt has a `## Response format` section"). Descriptions avoid `: ` because an unquoted YAML scalar with it does not parse. `read-only-audit` limits both agents to Read, Grep and Glob and sets `defaultMode: plan` and denies Edit, Write and NotebookEdit for the session. Start from one with `squad new --template <id>`, or from the welcome screen and the create flow of the interface.
- **`squad card`** looks in `--preset`, else the equipped preset, else the one preset that has the agent. The permission bar goes plan (1) < default/dontAsk (2) < acceptEdits (3) < auto (4) < bypassPermissions (5), taken from the agent's `permissionMode`. Colors only on a color terminal.
- **Interface.** `i` imports (the preview is a screen; a dangerous preset needs a second, red confirmation whose focus starts on Cancel), `x` exports to a file in the current folder; gists are command-line only.
- **Not verified by a human:** the real `gh` calls; how the new screens look in a real terminal.

## Stage 6

Formats checked against the Claude Code documentation of 2026-10-24 (statusline, plugins, plugin marketplaces, skills, subagents) and `claude plugin validate` 2.1.309.

- **`.squadup`** holds one preset name; blank lines and `#` comments are skipped. `initial` cannot be pinned. The search goes from the current folder up to the root, so a *directory* named `.squadup` (squad's own `~/.squadup`) is skipped. A broken file is an error that names its path. The file only names a preset of the reader's own library, so a pin in a cloned repository cannot bring in agents. `squad run` says which file it used; an explicit name ignores the pin; `squad status` reports a mismatch (also `pinned` in `--json`).
- **Status line.** `statusLine` is `{"type":"command","command":…}` with optional `padding`, `refreshInterval`, `hideVimModeIndicator`; Claude Code sends the session JSON on stdin and shows the stdout, one row per line, and shows nothing when the command exits non-zero. `enable` keeps the user's whole object in `~/.squadup/statusline.json` and rewrites only `command`/`type`, so their `padding` and the like stay; settings.json is edited in place (same formatting as everything else), a copy of the previous file is kept in `statusline-settings.backup.json`, and `disable` puts the original value back byte for byte. The command is `'<squad binary>' statusline`, plus `--home` when the data folder is not `~/.squadup`.
- **What the line prints.** The user's line first (a shell with the same stdin, 4 s limit, killed on timeout; a failing line still shows what it printed), then ` ◆ <preset>` on its last line, amber unless `NO_COLOR`. Nothing is appended for Initial or when nothing is equipped. `squad run` sets `SQUADUP_RUN_PRESET` for its claude, and that session's line shows `◆ name (run)` instead. The command never captures Initial, never prints a welcome and always exits 0.
- **`disable` is careful.** If the `statusLine` is no longer ours (the user or `squad restore` changed it) nothing is touched and only the record is dropped. After `restore` or `undo` brought back an old settings.json, `enable` starts fresh and takes whatever line is there as the original. `statusLine` is not a managed key, so `use` keeps it and it never counts as drift. These operations are not in `squad log` and not covered by `squad undo`: `disable` is the way back.
- **Plugin.** `plugin/` has `.claude-plugin/plugin.json` (name `squadup`) and one skill, `skills/squad/SKILL.md`; the marketplace is `.claude-plugin/marketplace.json` at the repository root (the documented place, not a bare `marketplace.json`), and its entry has the same name as the manifest, as installs by name require. Plugin skills are namespaced, so the command is **`/squadup:squad`**; the docs say the bare `/squad` also works when no other command uses it. The skill is `disable-model-invocation: true`: only the user can start it (it can switch presets), and it costs about 20 tokens of context per session. It calls `squad status --json`, `squad list --json` and `squad use <name> --yes` and may never add `--force`, `--discard-edits` or `--save-edits` itself. If `squad` is missing it prints the install line of `scripts/install.sh`, which stage 7 creates: **that URL does not exist until the repository is published**. A plugin cannot ship agents with `permissionMode`, `hooks` or `mcpServers` anyway, and this one ships none.
- **Verified here:** `claude plugin validate` passes for the plugin and the marketplace; installing from the local marketplace into a throwaway `CLAUDE_CONFIG_DIR` works and lists one skill. **Not verified:** running `/squadup:squad` inside a live session (it costs model tokens), and how the status line looks in a real session.
- **Correction to an earlier statement.** Agent files in `~/.claude/agents` are picked up by a running session within a few seconds (a new `agents` folder needs a restart); whether a changed model or permission setting applies mid-session is not documented, so the skill says only that a new session is certain.

## Interface redesign (after the stage 6 review)

The author found the first interface plain; this pass changed how it looks and moves, not what it does.

- **Look.** One brand gradient (amber → pink → violet → blue) runs along the frame edges and through the wordmark; everything else is quiet. The selected row has a bar (`▌`) instead of an arrow, keys in the footer are keycaps, models are colored pills (one hue per family), effort is rising bars, permission modes are a bar that goes from green (asks a lot) to red (asks nothing). The main screen shows the agents of a preset as a **roster of tiles** (up to six per row, falling back to a one-line list when they do not fit), each framed in the agent's own Claude Code color. On wide terminals the agent editor adds a live tile and a highlighted preview of the file; the pane divider runs the full height.
- **Motion.** One frame clock (80 ms, only while `Env.Animate` is on) drives: the shining wordmark, the pulsing selection bar, the roster dealing in tile by tile when the selection changes, the description typing itself, a braille spinner while models are checked, the logo of the welcome screen (letters, eight agent colors popping in and rippling), and the equip celebration (confetti in the agent colors, agents checking in one by one, a gradient progress bar). Every animation is a pure function of the frame number, so a frame always draws the same picture and tests can step the clock by hand. `SQUADUP_NO_ANIM=1` turns all of it off (and so does the harness): the screens then show their final state at once.
- **Mouse.** The main screen takes the wheel (move) and clicks (select; a second click on the selected row opens it). This captures the mouse, so selecting text in the terminal needs Shift.
- **Not verified by a human:** how it looks and feels in a real terminal (colors, speed, flicker). The program was only driven in a pseudo terminal: it starts, draws, enables the mouse and truecolor, and quits cleanly.

### Redesign, second pass

Review of the first pass on a 245×75 terminal: the motion was too occasional, the screens left much of the space empty, the preset list was too small, and the tool had no big title like Claude Code's.

- **Responsive main screen.** Below 100×30 the compact layout stays (list of 22 cells, roster, three fact rows). From 100×30 it becomes: a header band with the wordmark in **block letters** (three rows of half blocks, or five rows of double cells from 120×44) beside a field of twinkling stars and the status of the config; **preset cards** on the left (a third of the width, 30 to 46 cells: name, the agents as colored squares, what it is for, a LIVE badge); on the right the roster of the selected preset with tiles that stretch (up to 30 cells, with the agent's role from 22), the **selected agent's prompt** beside the tiles, and a row of panels (settings, **context cost** chart per agent, **what equipping would change**, health, activity). Spare height goes to the panels. The screen stops growing at 200×50 and sits in the middle.
- **Other screens open in a window** (at most 120×36) in the middle of the terminal; on a tall terminal the window is only as high as its content (at least 22 rows) so that it does not float over empty space. Below 30 rows they take the whole height.
- **Continuous motion.** The gradient now *flows* (the frame edges, the title and the logo shift one step per frame, a loop with no seam); the stars twinkle; the selection bar and the equipped preset's tiles move: each of its agents has a four-bar equalizer in its border. The deal-in, typewriter, spinner, welcome wipe and equip celebration of the first pass stay.
- **Agents are navigable on the main screen.** `←→` pick an agent (heavy border), `a` or a second click opens its editor, a click picks a tile; the mouse also handles the cards. `Entry` carries the agents' colors and `Card` the roles, prompts, tool lists, per-agent token costs and lint findings the panels need. Bars use `■□` and `·` instead of `▰▱▁`, which some fonts draw as thin dashes.
- **Not verified by a human:** the look and the motion in a real terminal. A pseudo terminal run at 245×75, 120×40 and 80×24 starts, takes keys and mouse, redraws (about 65 KB/s at 245×75) and exits cleanly.

### Redesign, third pass

- **Frame.** The gradient runs around the whole frame (top, right side, bottom, left side) and flows with the clock, so the side borders have color too. The version of `claude` is shown once: in the header band on the main screen, in the frame's corner elsewhere.
- **A stable main screen.** The panels sit at a fixed height right under a region of fixed height, so nothing moves when presets have a different number of agents. The selected agent's prompt is in a fixed column on the right of that region; the tiles wrap in the column on the left, and fall back to a one-line list when they do not fit.
- **The agent editor is a workbench** from 100×24: the fields on the left (with the agent's tile and the checks), and on the right an inspector that shows the selected field in full and what its values mean: the whole description with tips from the linter, every model with its availability, the effort ladder, permission modes with their strength, the tools as a checklist, the colors, and the whole prompt, numbered and scrollable (`pgup`/`pgdn`, wheel). `p` shows the file as it will be saved. The editor takes the whole terminal, up to 200×44.
- **Prompts can be written, edited or loaded.** `enter` on Prompt opens a full-size editor (`ctrl+s` saves, `ctrl+l` loads a file into it, `esc` asks before dropping changes); `o` opens `$EDITOR`; `f` loads a Markdown file after showing what it replaces. A path may be typed, dropped on the terminal (quotes and escaped spaces are cleaned up) or start with `~`. A file with YAML frontmatter, such as another agent, gives its body only. The limit is 256 KB of UTF-8 text. `squad edit <preset> <agent> --prompt-file file.md` does the same without the interface. The prompt is copied, not linked: an agent file has no way to refer to another file.

### Redesign, fourth pass

- **No prompt panel on the main screen.** The prompt is read and edited in the agent editor (`a`), where it has room.
- **Agent tiles are all the same size, whatever the number of agents.** Compact layout: 17×7. Spacious layout: 13 rows high, and 30 to 42 cells wide depending only on the width of the terminal (about a quarter of it), so a preset with one agent and one with six show equal cards. A big tile has the slot and (for an equipped preset) a moving equalizer in its top edge, the name, a rule, **the role in two lines**, then labeled rows: model, effort, access, tools (as many chips as fit, then a count). ## Squads: shared context, flow and review loop

The author asked for a per-agent switch for shared context between agents (on by default, off for e.g. a code review), a compact way to keep the shared notes, a visible hierarchy of the agents and a loop when the last reviewer finds a defect.

- **Claude Code has no such switch (checked in the subagent documentation, v2.1.310).** Every non-fork subagent starts with a clean window and sees only the task it is given; a *fork* inherits the whole conversation but is started by Claude or `/subtask`, uses the main session's prompt and tools, and cannot be chosen per agent. The frontmatter has no field for it. So squadup adds the sharing itself.
- **How: a notes file the agents read and write.** The text goes into the prompt Claude Code receives, never into the stored files: `team.Compile` renders the files that `apply` writes and `runner` passes in `--agents`; the stored preset, its export and `squad edit` see the authored text. `squadShare: false` in an agent's frontmatter isolates it; Claude Code would ignore the field, but `Compile` removes it anyway, and the linter knows it. Sharing is the default and is never written out.
- **The notes format is the cheapest that keeps what git cannot tell.** One tagged fact per line (`D` decision+why, `X` ruled out, `!` open defect, `?` question, `>` handoff), at most 25 lines of 100 characters, same key means edit not append, fixed items are deleted, code is referenced as `path:line` and never pasted. The instruction is about 130 words for every sharing agent (a test caps it at 140). A `!` line is a work item, so "no line starts with `!`" is the exit of the loop with no extra bookkeeping.
- **Tools decide what an agent can do with the notes.** No Read/Bash/Grep: no notes, and the linter warns. Read but no Write/Edit/Bash: a shorter block tells it to end its answer with the lines to record, and the main agent's brief says to record them. An isolated gate reports its defects to the main agent the same way.
- **The flow lives in `preset.yaml`** (`flow: {gate, fix, rounds}`, all optional; an empty flow only means "in slot order"). The order is the slot order; the main agent is the lead and is not a step. `Validate` requires gate and fix to be two different agents of the preset; renaming an agent follows into the flow and removing one drops the loop (`PruneFlow`). The flow travels in the export format.
- **Where the flow is told.** To the main agent, as a block appended to its prompt. A preset with no main agent gets the block through `--append-system-prompt` when started with `squad run`. An *equipped* preset with no main agent cannot carry it (Claude Code has no place for it besides the main agent's prompt or a CLAUDE.md, which squadup does not touch): the CLI, the interface and `squad flow` say so. The notes block still works there.
- **Looks.** Agent tiles stay rounded, colored and filled with facts and gain a *context* line (`⇄ shared` teal, `⊘ isolated` amber); the squad's own cards (settings, cost, health, what equipping changes) became square, quiet boxes under a dotted `▪ SQUAD` band, while the agents sit under a gradient `◆ AGENTS` band with a **flow strip**: lead ▸ the order of the agents ↺ who checks and who fixes. The agent editor has a *Shared context* field with a colored pill and a two-sided explanation; the preset screen has a *Team flow* row that asks for the gate, the fixer and the rounds.
- **The lint checks what the notes and the flow need:** a sharing agent that cannot read files (warning), one that can read but not write (note), a main agent running a flow without the `Agent` tool (warning).
- **Templates.** `refactor-day` has a review loop (reviewer checks, refactorer fixes) with the reviewer isolated; `bug-hunt` has one with the tester as the gate. Neither has a main agent, so they run their flow under `squad run` / `squad try`.
- **Not verified:** a live session. The block texts and the flow were not run against the real Claude Code (it costs requests); what is checked is that the right bytes go to the right agents. Whether a model follows the 25-line limit and the loop wording is for a manual check: `squad run refactor-day`, ask for a refactoring, then `squad notes`.

### Flow diagram and wrapped checks

- **Lint output wraps.** Findings in the agent editor, the preset screen, the *Health* panel and the field inspector are wrapped under their mark, and the hint (`→ …`) is shown with them; nothing is cut off with `…`. On a small window the preset screen drops the hints and lists errors before warnings, so an error never falls off the bottom.
- **The flow is drawn.** From 38 rows the main screen replaces the one-line strip of a preset that has a flow with a diagram: the lead (`◆ main agent`, or `you`), the agents in slot order along arrows, `⊘` on isolated agents, and, for a review loop, an arc under them from the gate (`│`) back into the agent that fixes (`▲`), labelled `↺ <gate> finds defects · up to N` (inside the arc, after it, or shortened to `↺ ×N` as the width allows). One arrow at a time lights up in turn, then the arc; frame 0 and `SQUADUP_NO_ANIM=1` draw it still. When it does not fit the width, the strip is shown instead.

## Live token report (replaces the context-cost estimate)

The author found the estimated "context cost" not worth having and asked for a readable report, in real time, of the tokens each agent and the whole squad really spend.

- **The estimate is gone** from the main screen and the cards (`Card.Costs`, `Card.SessionTokens`, the *CONTEXT COST* panel and the `~N tokens/session` lines). `squad lint` still reports it in its own output; nothing else shows it.
- **Where the numbers come from (checked on a real run, Claude Code 2.1.310, one haiku subagent, a few cents, with the author's consent).** The documentation says only that subagent transcripts are `~/.claude/projects/{project}/{sessionId}/subagents/agent-{agentId}.jsonl`. A real run showed the rest: a `agent-<id>.meta.json` beside each with `agentType` (the agent's name), `finished`, `toolUseId`, `spawnDepth`; every `assistant` record has `message.id`, `message.model` and `message.usage` (`input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, `output_tokens`); a message with several content blocks is written as several records that all carry the whole message's usage, so a message must be counted once. The sums over unique messages equal what Claude Code writes as `toolUseResult.usage` for the run, and its `totalTokens` is input + cache writes + output (cache reads left out), which is also what TOTAL means here. The project folder is the working folder's real path with every non-alphanumeric character replaced by `-`.
- **`internal/usage`** reads a session's transcripts incrementally (an offset per file, a line still being written waits for the next read, a message seen again replaces its earlier record because the output grows while it streams) and groups by agent: the main session first, then the subagents by their meta `agentType`, the heaviest first. A run whose meta says it has not finished counts as *working* only while its file has been written to in the last two minutes, so a closed session does not stay "working".
- **The interface** reads it every second (`Env.Live`; tests send the clock by hand): the *Usage* screen (`u`, or `squad usage --watch`) with the table, shares, a sparkline of the pace, the cache hit rate, and `z` to count from now; and the *TOKENS · LIVE* panel on the main screen. It follows the newest session of the folder the interface was started in, and moves to a newer one when it appears. Colors: the session itself is Claude's orange, an agent of the equipped preset its own color, any other a fixed one by its name.
- **The CLI.** `squad usage` prints the table once (`--json`, `--session`, `--dir`); after `squad run` the table of that session is printed when claude exits.
- **Not verified:** a long live session with several simultaneous agents, nested subagents (their files are read like any other, `spawnDepth` is not used), agent teams, and what the numbers do after a compaction.

### The model check shows itself

"Check which models I can use" asked for consent and then did nothing visible: the four requests ran in the background (a few seconds), the welcome screen showed a spinner line only if it was drawn, and the end was a short-lived hint. It is now a screen of its own (`modelCheck`): each of fable, opus, sonnet and haiku shows *asking…* with a spinner, then `✓ available` with the full model ID or `✗ unavailable` with Claude's reason, wrapped; the end says how many of four are available and that unavailable ones are greyed out in the model lists. `esc` stops a running check and cancels its requests; when it is done any key closes it. `models.ProbeEach` and `Workspace.ProbeModelsEach` report each result as it arrives. The check can also be started from the main screen with `m`. Without claude, or when it is not logged in, the screen says so and that nothing was sent.
